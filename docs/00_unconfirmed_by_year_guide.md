# 00. 연도별 결과 미확인 공고 사전 점검 — 실행 및 검증 가이드

## 1. 목적과 분석 범위

입찰공고의 결과 연결 상태를 **공고 단위**로 구분하고, 실제 공고일(`pblancDate`) 기준으로 **연도별 결과 미확인 건수와 비율**을 산정한다. 이후 A1~A4의 유찰률 분석과 KPI 평가에서 결과 미확인 공고를 유찰이나 낙찰로 임의 분류하지 않기 위한 선행 점검이다.

- **공식 실행 코드:** [`scripts/analysis/00_unconfirmed_by_year.py`](../scripts/analysis/00_unconfirmed_by_year.py)
- **커밋된 결과:** [`data/analysis/unconfirmed_by_year.csv`](../data/analysis/unconfirmed_by_year.csv)
- **자료:** 입찰공고 CLEAN, 입찰결과 CLEAN (계약정보 미사용)
- **분석 단위:** 공고키에 대응하는 입찰공고 행. 코드에서는 입찰공고의 **완전 동일 행 중복만** 제거하고 연도별 건수를 집계한다.
- **집계 대상 연도:** CLEAN에 실린 **실제 공고일 전체 연도**. 수집 파일명은 2021~2025년이지만 실제 2020년·2026년 공고도 현황표에 남긴다. 후속 본 분석에서는 별도 기간 필터를 적용한다.

> **주의:** 이 스크립트의 '결과 미확인'은 **공고키 직접매칭도 없고, 취소공고도 아니고, 동일 사업키의 다른 공고 결과도 없는 경우**다. 단순히 '직접매칭이 안 된 모든 공고'와 다르다. A5의 '후속공고 미확인'과도 다른 지표다.

## 2. 입력 파일과 필수 컬럼

프로젝트 루트의 `data/clean/`에 다음 **정확한 파일명**이 필요하다.

| 입력 | 파일명 | 필수 컬럼 |
|---|---|---|
| 입찰공고 | `bid_notice_clean_20210101_20251231.csv` | `demandYear`, `orntCode`, `dcsNo`, `pblancNo`, `pblancOdr`, `pblancSe`, `pblancDate` |
| 입찰결과 | `bid_result_clean_20210101_20251231.csv` | `demandYear`, `orntCode`, `dcsNo`, `pblancNo`, `pblancOdr` |

- **공고키(직접매칭):** `demandYear + orntCode + dcsNo + pblancNo + pblancOdr`
- **사업키(다른 공고 결과 확인):** `demandYear + orntCode + dcsNo`
- CSV는 `utf-8-sig`로 읽고, 키 컬럼은 **문자열**로 처리하여 앞자리 0을 보존한다.
- 키의 양끝 공백과 빈 문자열을 정리하고, 매칭에 필요한 키에 결측값이 있으면 해당 기준으로 매칭하지 않는다.
- 필수 열·파일이 없으면 오류로 중단한다. `pblancDate`는 `YYYYMMDD` 형식으로 변환하며 누락·변환 오류가 있으면 중단한다.

## 3. 실행 방법

**프로젝트 루트**(`C:\workspace\defense-procurement-risk-dashboard`)의 PowerShell 또는 VS Code 터미널에서 실행한다.

```powershell
cd C:\workspace\defense-procurement-risk-dashboard
python -m pip install -r requirements.txt
python scripts/analysis/00_unconfirmed_by_year.py
```

완료 시 `data/analysis/unconfirmed_by_year.csv`를 생성·갱신하고 콘솔에 매칭 건수와 연도별 Markdown 표를 출력한다. 이 스크립트는 명령행 `--data-dir` 인자를 지원하지 않으므로 다른 CLEAN 위치를 사용하려면 코드의 `INPUT_DIR`을 수정해야 한다.

## 4. 분류 절차와 계산식

입찰공고에서 완전 동일 행을 제거한 뒤, 아래 조건을 **순서대로** 적용한다. 네 집단은 서로 중복되지 않는다.

1. **결과 직접매칭:** 5개 공고키가 입찰결과에 모두 일치하는 공고.
2. **취소공고:** 직접매칭이 없고 `pblancSe == "취소공고"`인 공고.
3. **동일사업 다른 공고 결과 존재:** 앞 두 범주가 아니며, 동일 3개 사업키에 해당하는 입찰결과가 존재하는 공고.
4. **결과 미확인:** 앞의 세 범주 어디에도 해당하지 않는 공고.

연도 구분은 **`pblancDate` 기준**이며, 아래 두 비율의 **분모를 구분**해야 한다.

```text
해당 연도 공고 중 미확인 비율(%) = 해당 연도 결과 미확인 수 / 해당 연도 전체 공고 수 × 100
전체 미확인 중 비중(%)       = 해당 연도 결과 미확인 수 / 전체 연도 결과 미확인 수 × 100
```

코드는 각각 소수점 둘째 자리까지 반올림한다. 합계 행의 첫 번째 비율은 전체 공고 대비 미확인률, 두 번째 비율은 100.00%이다.

현황표에는 파일명 기준 기간 바깥의 공고일(2020년 118건, 2026년 1건)도 포함돼 있다. **2021~2025년만 사용하는 후속 위험도·KPI 분석의 모집단이 61,142건이라는 뜻은 아니다.**

### 상태별 전체 건수 대조

다음 값은 CLEAN 기준 데이터 항목 정의서와 프로젝트 정의서에 기재된 상태별 집계이며, 스크립트가 콘솔에서 출력하는 분류 항목과 대응한다.

| 분류 | 공고 수 |
|---|---:|
| 공고키 결과 직접매칭 | 38,025 |
| 취소공고 | 5,578 |
| 동일사업 다른 공고 결과 존재 | 3,770 |
| 결과 미확인 | 13,769 |
| **합계** | **61,142** |

`38,025 + 5,578 + 3,770 + 13,769 = 61,142`. 이 가운데 **결과 직접매칭은 결과확정과 같지 않다**. 동일 공고의 결과가 상충하는 `판단보류` 등이 있을 수 있으므로, 이후 유찰률의 분모는 별도의 결과 상태 확정 로직을 적용한다.

## 6. 검증과 해석상 주의

- **중복 처리:** 본 스크립트는 완전 동일 공고 행만 `drop_duplicates()`로 제거한다. 공고키 중복 0건이라는 결론을 이 스크립트만으로 내릴 수 없다. 실행 로그의 '완전 중복 제거' 수를 확인한다.
- **합계 확인:** 연도별 공고 수 합계와 미확인 수 합계를 코드가 검사한다. 미확인 합계가 13,769건과 다르면 오류로 중단하는 대신 **[확인 필요] 경고**를 출력하며 현재 입력으로 계산한 결과를 저장한다.
- **2020·2026년:** 연도별 현황에는 보존하지만 2021~2025년 분석과 섞지 않는다.
- **미확인의 의미:** 직접 결과가 없다고 모두 결과 미확인은 아니다. 취소공고와 동일사업 다른 공고 결과 존재는 별도 상태다.
- **사후 결과 정보:** 입찰결과 연결은 결과 상태를 진단하기 위한 것이며, 신규 공고의 사전 위험도 입력 피처로 사용하지 않는다.
- **개찰일 역전:** 공고일보다 개찰일이 빠른 공고를 검사·제외하는 로직은 **이 00번 스크립트에 없다**. 해당 점검은 별도 분석·검증의 범위로 구분해야 한다.
- **재현 확인:** 현재 로컬 CLEAN을 이용해 스크립트를 재실행한 뒤, 생성된 CSV를 GitHub에 커밋된 결과와 비교한다. 이번 가이드는 GitHub 코드·저장된 출력에 근거하며 현 환경에서 CLEAN 재실행까지 수행한 것은 아니다.
